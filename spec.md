# UniMate — продуктовая и техническая спецификация MVP

- **Версия:** 1.0
- **Статус:** baseline для реализации
- **Продукт:** Telegram-бот для учебных задач студентов SDU

## 1. Vision

UniMate помогает студентам SDU держать учебные дедлайны в одном простом месте: добавить задачу за несколько шагов, быстро проверить ближайшие дела и получить напоминание до срока сдачи.

## 2. Problem Statement

Учебные дедлайны приходят из разных источников — сообщений преподавателей, учебных платформ и чатов. Студенту приходится вручную переносить информацию в собственный список или помнить её. Из-за этого задачи теряются, а дедлайны забываются.

UniMate предоставляет единый минимальный список задач в Telegram с напоминанием за час до дедлайна.

## 3. Целевая аудитория и продуктовые границы

**Primary persona:** студент SDU, который использует Telegram и хочет фиксировать учебные задания без отдельного приложения.

**Платформа:** личный чат Telegram с ботом.

**Язык интерфейса MVP:** русский.

**Временная зона интерфейса:** `Asia/Almaty`.

## 4. Цели и не-цели

### Цели

- Создать задачу с названием и дедлайном.
- Просмотреть активные задачи и задачи, дедлайн которых приходится на сегодня.
- Отметить задачу как выполненную.
- Получить однократное напоминание за час до дедлайна.
- Сохранять задачи между перезапусками процесса.

### Не-цели

- AI/LLM, свободный ввод в стиле «сдать лабу в пятницу» или автоматическое извлечение дедлайна из пересланных сообщений.
- Импорт/синхронизация с Moodle, Google Classroom, Google Calendar или другими системами.
- Групповые чаты, совместные задачи, курсы и роли преподавателей.
- Редактирование/удаление задачи после создания.
- Повторяющиеся задачи, вложения, теги, приоритеты, статистика, web app и платежи.
- Гарантия отправки напоминаний, когда бот выключен или Telegram недоступен.

## 5. Пользовательские сценарии

### UC-1: Начать работу

1. Пользователь открывает личный чат и отправляет `/start`.
2. Бот кратко объясняет назначение и показывает доступные действия.
3. Пользователь может добавить задачу, открыть список задач, посмотреть задачи на сегодня или вызвать `/help`.

### UC-2: Создать задачу

1. Пользователь нажимает «Добавить задачу» или отправляет `/add`.
2. Бот просит ввести название.
3. Пользователь вводит непустое название длиной 1–200 символов после удаления пробелов по краям.
4. Бот просит ввести дедлайн в формате `ДД.ММ.ГГГГ ЧЧ:ММ`, например `20.10.2026 23:59`.
5. Бот проверяет формат и то, что дедлайн находится в будущем.
6. Бот сохраняет задачу и показывает подтверждение с названием и локальным временем дедлайна.
7. Если ввод некорректен, бот объясняет ожидаемый формат и предлагает повторить ввод.
8. Пользователь может отправить `/cancel` на любом шаге до сохранения; незавершённая задача не сохраняется.

### UC-3: Просмотреть активные задачи

1. Пользователь нажимает «Мои задачи» или отправляет `/tasks`.
2. Бот показывает активные (`pending`) задачи по возрастанию дедлайна.
3. Для каждой задачи показываются название, дедлайн в `Asia/Almaty` и действие «Выполнено».
4. Если активных задач нет, бот сообщает об этом и предлагает добавить первую задачу.
5. Если задач много, список разбивается на страницы по 10 задач с кнопками навигации.

### UC-4: Просмотреть задачи на сегодня

1. Пользователь нажимает «На сегодня» или отправляет `/today`.
2. Бот показывает только активные задачи, дедлайн которых попадает в текущий календарный день по `Asia/Almaty`.
3. Задачи сортируются по времени дедлайна.
4. При отсутствии задач бот сообщает, что на сегодня активных дедлайнов нет.

### UC-5: Отметить задачу выполненной

1. Пользователь нажимает «Выполнено» под своей задачей.
2. Бот проверяет, что задача принадлежит отправителю callback и ещё активна.
3. Бот меняет статус на `completed` и подтверждает действие.
4. Выполненная задача больше не отображается в активных списках, а её напоминание не отправляется.
5. Повторное нажатие безопасно: бот сообщает, что задача уже выполнена или недоступна.

### UC-6: Получить напоминание

1. Для каждой новой задачи создаётся время напоминания `deadline_at - 1 час`.
2. Фоновый worker периодически проверяет задачи, ожидающие напоминания.
3. Если задача всё ещё `pending`, её дедлайн в будущем и время напоминания наступило, бот отправляет одно напоминание.
4. После успешной отправки система сохраняет факт отправки.
5. Если до дедлайна при создании задачи осталось меньше часа, напоминание отправляется при ближайшей проверке worker (обычно в течение 30 секунд).
6. Если процесс был остановлен, после запуска worker обрабатывает пропущенные напоминания для задач, дедлайны которых ещё не наступили. Напоминания о уже прошедших дедлайнах не отправляются.

## 6. Команды и интерфейс

| Команда/действие | Поведение |
|---|---|
| `/start` | Приветствие, краткое описание и главная клавиатура |
| `/help` | Короткая инструкция по командам и формату дедлайна |
| `/add` | Запустить мастер создания задачи |
| `/tasks` | Показать все активные задачи постранично |
| `/today` | Показать активные задачи на текущий день в `Asia/Almaty` |
| `/cancel` | Отменить текущий мастер создания задачи |
| `Добавить задачу` | Эквивалент `/add` |
| `Мои задачи` | Эквивалент `/tasks` |
| `На сегодня` | Эквивалент `/today` |
| `Выполнено` | Отметить соответствующую задачу выполненной |

Кнопки и команды не должны дублировать бизнес-логику: оба варианта вызывают общий service layer.

## 7. Функциональные требования

- **FR-1:** бот работает в личном чате. В группах сценарии MVP не поддерживаются.
- **FR-2:** пользователь может создать задачу с непустым названием до 200 символов и будущим дедлайном.
- **FR-3:** дата вводится строго в формате `ДД.ММ.ГГГГ ЧЧ:ММ` и интерпретируется в `Asia/Almaty`.
- **FR-4:** ошибки ввода объясняются понятным сообщением; ошибочное значение не приводит к сохранению задачи.
- **FR-5:** пользователь видит только свои задачи.
- **FR-6:** `/tasks` показывает все активные задачи по дедлайну, страницы содержат не более 10 задач.
- **FR-7:** `/today` показывает задачи с локальным дедлайном в пределах текущего дня, включая начало дня и не включая начало следующего дня.
- **FR-8:** активную задачу можно пометить выполненной.
- **FR-9:** для каждой активной задачи отправляется не более одного напоминания, когда наступает `deadline - 1 hour`.
- **FR-10:** задача и факт отправки напоминания сохраняются в постоянном хранилище.
- **FR-11:** после перезапуска worker восстанавливает ожидающие напоминания из БД.
- **FR-12:** в приложении отсутствуют реальные секреты; конфигурация берётся из переменных окружения.

## 8. Нефункциональные требования

- **Безопасность данных:** все операции чтения и изменения ограничены Telegram ID текущего пользователя. SQL выполняется через параметризованные запросы.
- **Надёжность:** исключение при обработке одного напоминания не должно завершать весь worker.
- **Повторный запуск:** задачи и статусы не теряются при перезапуске процесса.
- **Поддерживаемость:** Telegram handlers, бизнес-логика, SQL-доступ и конфигурация разделены по модулям.
- **Минимальные данные:** не запрашивать имя, телефон, email или университетский логин. Достаточно Telegram user ID и данных задачи.
- **Логирование:** записывать ошибки и старт/остановку worker, не логировать токены и содержимое `.env`.
- **Ограничение MVP:** отправка напоминаний требует работающего процесса и доступности Telegram API.

## 9. Техническая архитектура

### Стек

- Python 3.12+
- aiogram 3.x
- SQLite через aiosqlite
- python-dotenv
- asyncio для фонового worker
- pytest

### Поток запроса

`Telegram Update → Router/Handler → Service → Repository → SQLite`

Напоминания обрабатывает отдельная asyncio-задача, которая периодически обращается к repository и отправляет сообщения через Bot API.

### Предлагаемая структура

```text
app/
  main.py
  config.py
  handlers/
    start.py
    tasks.py
  services/
    task_service.py
    reminder_service.py
  repositories/
    task_repository.py
  db/
    connection.py
    schema.sql
  keyboards/
    main_menu.py
    task_list.py
tests/
  unit/
  integration/
.env.example
.gitignore
requirements.txt
README.md
AGENT.md
process.md
spec.md
roles/pm.md
```

Структура является ориентиром; добавлять отдельный модуль можно, только если он отвечает за отдельную обязанность.

## 10. Модель данных

### Таблица `tasks`

| Поле | Тип / ограничение | Назначение |
|---|---|---|
| `id` | INTEGER PRIMARY KEY | Внутренний ID задачи |
| `telegram_user_id` | INTEGER NOT NULL, indexed | Владелец задачи |
| `title` | TEXT NOT NULL | Название после trim, длина 1–200 |
| `deadline_at` | TEXT NOT NULL | Дедлайн в UTC ISO-8601 |
| `status` | TEXT NOT NULL, `pending`/`completed` | Текущий статус |
| `created_at` | TEXT NOT NULL | Время создания в UTC ISO-8601 |
| `completed_at` | TEXT NULL | Время выполнения в UTC ISO-8601 |
| `reminder_sent_at` | TEXT NULL | Время успешной отправки напоминания |

Время напоминания вычисляется как `deadline_at - 1 hour`, поэтому отдельно хранить `reminder_at` не обязательно. При построении выборки нужно сравнивать timezone-aware UTC timestamps. Если при реализации удобнее хранить `reminder_at` отдельно, это допустимо только при сохранении описанного поведения и обновлении этой спецификации.

Индексы: как минимум индекс по `(telegram_user_id, status, deadline_at)`; добавление индекса по полю `reminder_sent_at` допустимо для оптимизации worker.

## 11. Напоминания и пограничные случаи

- Worker запускается при старте приложения и проверяет ожидающие напоминания каждые 30 секунд.
- К отправке подходят задачи, у которых статус `pending`, `reminder_sent_at IS NULL`, дедлайн строго позже текущего времени и `deadline_at - 1 hour <= now`.
- После успешного ответа Telegram API записывается `reminder_sent_at`.
- Если отправка завершилась ошибкой, ошибка логируется, а задача остаётся кандидатом на повторную попытку при следующем цикле до дедлайна.
- Выполненная или просроченная задача не получает напоминание.
- Один процесс приложения предполагается для MVP. Горизонтальное масштабирование нескольких экземпляров не поддерживается.

## 12. Конфигурация и локальный запуск

Переменные окружения:

- `BOT_TOKEN` — обязательный токен Telegram-бота.
- `DB_PATH` — путь к файлу SQLite, например `data/unimate.sqlite3`; значение по умолчанию должно быть безопасным локальным путём.
- `TIMEZONE` — по умолчанию `Asia/Almaty`.
- `LOG_LEVEL` — по умолчанию `INFO`.

Репозиторий должен содержать `.env.example`, но не `.env`. При отсутствии `BOT_TOKEN` приложение должно завершаться с понятной ошибкой до запуска polling.

README должен объяснять создание виртуального окружения, установку зависимостей, настройку `.env`, запуск и выполнение тестов.

## 13. Тестирование и критерии готовности MVP

Обязательные тесты:

- корректный формат даты, невалидный формат и прошедший дедлайн;
- пустое и слишком длинное название;
- одна учётная запись не может читать/завершать задачу другой;
- выборка задач «на сегодня» работает на границах локального дня;
- `/tasks` сортирует активные задачи и поддерживает пагинацию;
- задача меняет статус только один раз безопасным образом;
- напоминание отправляется один раз;
- завершённые и просроченные задачи пропускаются;
- при рестарте worker подбирает ожидающие напоминания с будущим дедлайном;
- ошибка отправки одного напоминания не останавливает worker.

MVP считается готовым, когда все FR реализованы, тесты проходят, локальный запуск описан, и не остаётся известных проблем с изоляцией данных.
