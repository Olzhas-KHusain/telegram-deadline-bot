# Процесс разработки UniMate (Spec-Driven Development)

## 1. Основной принцип

Спецификация определяет **что** нужно построить, Issue описывает ограниченную порцию работы, а код является реализацией требований. AI не должен самостоятельно расширять продукт или трактовать неопределённость как разрешение добавить функцию.

Поток работы:

`Vision → spec.md → GitHub Issue → план AI → реализация → тесты → PR → review → merge`

## 2. Перед началом работы над Issue

1. Прочитай `AGENT.md`, соответствующий раздел `spec.md` и Issue целиком.
2. Проверь зависимости Issue и текущее состояние репозитория.
3. Сформулируй короткий план: файлы, изменения поведения, тесты и возможные риски.
4. Если требование конфликтует со спецификацией или требует продуктового решения, остановись и вынеси вопрос в Issue/PR. Не делай скрытых предположений.
5. Не редактируй посторонние части проекта ради удобства реализации.

## 3. Разработка

- Одна ветка на одну Issue.
- Один PR на одну Issue, если команда явно не согласовала другое.
- Делай небольшие изменения и запускай связанные тесты после каждого существенного этапа.
- Сначала реализуй доменную логику и тесты, затем интеграцию с Telegram, если это не конфликтует с планом Issue.
- Не используй реальный токен и Telegram API в автоматических тестах.
- Если AI не может выполнить команду или тест из-за отсутствующей зависимости/секрета, сообщи об этом явно, не заявляй, что проверка прошла.

## 4. GitHub Issues

Каждая Issue должна включать:

- **Context:** зачем нужна работа и какую пользовательскую проблему решает.
- **Requirements:** наблюдаемое требуемое поведение.
- **Technical Implementation Steps:** ориентир по реализации без навязывания каждой строки кода.
- **Acceptance Criteria:** проверяемые условия завершения.
- **Dependencies:** какие Issue должны быть закрыты ранее.

Не закрывай Issue только потому, что код написан. Сначала проверь каждый Acceptance Criterion.

## 5. Pull Request

Название PR: `[Issue #N] <краткое описание>`.

Описание PR должно содержать:

```text
## What changed
- ...

## Acceptance Criteria
- [x] ...
- [x] ...

## Tests
- Команды и фактический результат

## Risks / Notes
- Ограничения, миграции или известные проблемы

Closes #N
```

Не отмечай критерий выполненным, если он не проверен. Для UI/бота приложи примеры сообщений или скриншоты тестового чата, если это полезно и безопасно.

## 6. Code review

Ревьюер проверяет:

- соответствие `spec.md` и Issue;
- выполнение Acceptance Criteria;
- изоляцию данных по Telegram ID;
- валидацию ввода и обработку времени;
- устойчивость фонового процесса напоминаний;
- тесты положительных и отрицательных сценариев;
- отсутствие секретов и лишних зависимостей.

Если есть замечания, AI исправляет их в той же ветке и добавляет/обновляет тесты.

## 7. Definition of Ready

Issue готова к реализации, если её цель понятна, требования не противоречат `spec.md`, зависимости известны, Acceptance Criteria проверяемы и задача помещается в один небольшой PR.

## 8. Definition of Done

- все Acceptance Criteria проверены;
- тесты проходят локально и в CI (если CI настроен);
- форматирование/линтинг проходят, если включены в проект;
- документация обновлена при необходимости;
- PR прошёл ревью и связан с Issue;
- не осталось случайных изменений, секретов или локальных файлов.
