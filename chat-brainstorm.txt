Почему стоит рассмотреть: понятная проблема, ограниченный набор функций и возможность продемонстрировать работу с базой данных, планировщиком задач, Telegram Bot API и асинхронными процессами.

Концепция № 2. QueueMate — мониторинг очередей в популярных местах

Проблема: перед походом в столовую, кофейню, спортзал или другое популярное место человек не знает, насколько там загружено. Приходится идти наугад.

Решение: бот показывает актуальную загруженность заведений благодаря сообщениям самих пользователей.

Пример использования:

Пользователь открывает бота и выбирает:

Возможности MVP:

Список заранее добавленных мест.

Возможная фишка: бот учитывает давность сообщений и не выдаёт старую информацию за актуальную. Например, отчёт пятиминутной давности считается свежим, а получасовой — уже нет.

Сложность: средняя.

1. Зафиксируем концепцию UniMate
Vision

UniMate помогает студентам SDU организовывать учебные задачи, отслеживать дедлайны и вовремя получать напоминания, используя привычный интерфейс Telegram.

Problem Statement: учебные задания и сроки их сдачи разбросаны по чатам и образовательным платформам. Студентам приходится самостоятельно собирать эту информацию и помнить о предстоящих дедлайнах, из-за чего некоторые задачи могут быть забыты.

Решение: простой Telegram-бот, который позволяет записывать учебные задачи, просматривать предстоящие дедлайны и получать автоматические напоминания.

Что войдёт в MVP

Мы специально ограничиваем первую версию несколькими основными функциями.

Завершение задачи	Отметка выполненной задачи одной кнопкой

Хранение данных	SQLite сохраняет задачи после перезапуска бота

Интерфейс первой версии будет на русском языке. Время будет отображаться в часовом поясе Asia/Almaty.

Пока не будем добавлять AI, интеграцию с Moodle, веб-интерфейс или синхронизацию с календарями. Эти функции интересны, но сейчас они увеличат объём работы, не являясь необходимыми для проверки основной идеи.

4. Как теперь работать по Spec-Driven Development

Здесь важен один момент: не нужно отправлять AI все пять Issues одновременно и просить реализовать проект целиком.

Это противоречило бы самой идее управляемой разработки: AI мог бы начать создавать несколько взаимозависимых компонентов одновременно, а ошибки было бы сложнее обнаружить.

Рекомендуемый процесс:

Шаг 1. Создай GitHub-репозиторий.

Назови его unimate и добавь подготовленные документы в корень проекта. Файл roles/pm.md должен находиться в каталоге roles/.

Шаг 2. Перенеси пять Issues в GitHub.

Используй файл GITHUB_ISSUES.md или отдельные файлы из каталога issues/. Порядок реализации уже определён.

Шаг 3. Передай AI-кодеру первую задачу.

Вместе с Issue № 1 он должен получить AGENT.md и spec.md. Первый документ определяет правила разработки, второй — требования к продукту.

Шаг 4. Проверь результат первой задачи.

Убедись, что проект запускается, конфигурация работает, тесты проходят и структура соответствует документации. Затем проведи ревью и объедини изменения через PR.

Шаг 5. Переходи к следующей Issue.

После завершения каждой задачи AI должен учитывать уже существующий код, а не создавать параллельную реализацию тех же компонентов.

Такой подход позволяет не только получить работающий бот, но и контролировать качество архитектуры на каждом этапе.

Важное решение по архитектуре

Я предусмотрел обработку напоминаний через отдельную фоновую задачу asyncio, а не через дополнительные библиотеки-планировщики.

Для небольшого MVP этого достаточно. При этом напоминания сохраняют состояние в SQLite, поэтому после перезапуска бот может восстановить ожидающие уведомления.

Есть ограничение: бот должен постоянно работать, чтобы вовремя отправлять напоминания. Если процесс остановлен, уведомления в этот период не отправляются. Конфигурация конкретного хостинга не включена в MVP, но документация предусматривает локальный запуск.

Это разумный компромисс для первой версии: мы не усложняем инфраструктуру, сохраняя необходимую функциональность.

Следующий шаг — создать GitHub-репозиторий, добавить документацию и начать с Issue № 1. После этого разработка UniMate пойдёт по чёткому плану, где у каждой задачи есть конкретный результат и проверяемые критерии готовности.
